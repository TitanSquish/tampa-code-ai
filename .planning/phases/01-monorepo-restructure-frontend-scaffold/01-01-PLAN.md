<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Working directory → filesystem | `git mv` and plain `mv` operate on repo files; incorrect target path would leak secrets or break boot |
| Repo → git remote | `.gitignore` controls what leaves the developer machine in a push; a wrong rule would leak `.env` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Information Disclosure | `.env` file move | mitigate | Move `.env` with plain `cp`/`rm` (NOT `git mv` — it would error on an untracked file but also surface the filename). Verify with `git check-ignore -v backend/.env` after move (acceptance criterion in Task 2). |
| T-01-02 | Information Disclosure | `.gitignore` pattern for PDFs | mitigate | Replace `data/*.pdf` with `**/data/*.pdf` so `backend/data/tampa-code-5-27.pdf` remains ignored; acceptance criterion runs `git check-ignore` on the PDF. |
| T-01-03 | Information Disclosure | `backend/.env.example` content | mitigate | Task 2 action lists ONLY placeholder values (`sk-...`, `change-this-*`). Acceptance criterion greps for any real-looking `sk-[a-zA-Z0-9]{20,}` and rejects. |
| T-01-04 | Tampering | `git mv` vs `cp` confusion | accept | `git mv` preserves history and stages the rename atomically. Risk of accidental content change is near zero — no edit is performed. |
| T-01-05 | Denial of Service | Flask fails to boot from `backend/` after move | mitigate | Task 1 acceptance criterion runs `cd backend && python -c "import code_website"` — failure blocks the plan from completing. |

**ASVS Level 1 applicability:** No auth, session, crypto, or input-validation flows are introduced in Phase 1. The only ASVS-relevant controls are secret-handling (V14.3 — env vars not committed), addressed by T-01-01 and T-01-03.
</threat_model>
