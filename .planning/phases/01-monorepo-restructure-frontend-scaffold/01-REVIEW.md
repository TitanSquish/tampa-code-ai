# Phase 1: Code Review Report

**Reviewed:** 2026-04-16
**Depth:** standard

## Summary

This phase restructured a Flask monolith into a monorepo (`backend/` + `frontend/`) and scaffolded a Vite + React + TypeScript + Tailwind v4 + shadcn/ui frontend. Backend files were moved without modification. The frontend scaffold is clean and well-structured. Two critical issues exist: a hardcoded fallback secret key in `code_website.py` and the `.env.example` shipping a partial OpenAI key prefix that gives reviewers a false sense of safety. Four warnings cover config/structural concerns that will affect Phase 2 and Phase 4. Five informational items address dead code, naming, and minor config gaps.

## Critical Issues

### CR-01: Hardcoded fallback `FLASK_SECRET_KEY` allows session forgery if env var not set

**File:** `backend/code_website.py:44`
**Issue:** The `secret_key` assignment falls back to the literal string `"change-this-secret"` when `FLASK_SECRET_KEY` is not present in the environment. Flask uses `secret_key` to sign session cookies. Any deployment that launches without the env var set is silently insecure — an attacker who knows (or guesses) the default value can forge a session cookie and bypass authentication.
**Fix:**
```python
_secret = os.getenv("FLASK_SECRET_KEY")
if not _secret:
    raise RuntimeError(
        "FLASK_SECRET_KEY environment variable is not set. "
        "Generate one with: python -c \"import secrets; print(secrets.token_hex(24))\""
    )
app.secret_key = _secret
```
Same pattern applies to `LOGIN_PASSWORD` on line 46 — the fallback `"test123"` means a forgotten env var exposes the app with a trivially guessable password. Both should fail loudly at startup rather than silently use insecure defaults.

### CR-02: `.env.example` ships a partial real-looking OpenAI key prefix

**File:** `backend/.env.example:6`
**Issue:** `OPENAI_API_KEY=sk-...` uses the real `sk-` prefix. This is not itself a leak, but if a developer copies `.env.example` to `.env` and accidentally commits `.env`, the presence of a recognisable key format makes it easier to miss during a git diff review (the value looks like it was intentionally set). More concretely, secret-scanning tools (e.g., GitHub's push protection, Gitleaks) key off `sk-` followed by characters — this placeholder could produce false positives that train developers to ignore the scanner. Use a clearly fake placeholder that does not match the real format.
**Fix:**
```
OPENAI_API_KEY=YOUR_OPENAI_API_KEY_HERE
```

## Warnings

### WR-01: `tsconfig.json` root defines `paths` but no `baseUrl` resolution for project references

**File:** `frontend/tsconfig.json:7-9`
**Issue:** The root `tsconfig.json` sets `"baseUrl": "."` and `"paths": { "@/*": ["./src/*"] }` at the top level, but this file has `"files": []` and only acts as the composite project root. TypeScript project references do not inherit `paths` from the root config into `tsconfig.app.json`. Because `tsconfig.app.json` already independently declares the same `paths` (lines 25-26), the duplicate in `tsconfig.json` is dead weight that can mislead tooling. The real risk is that if `tsconfig.app.json` is ever regenerated by a scaffold tool and loses its own `paths`, the `@/` alias will silently stop resolving for the build, while editor autocomplete may continue to work through the root config.
**Fix:** Remove `compilerOptions` from `frontend/tsconfig.json` entirely. Alias resolution should live solely in `tsconfig.app.json` (for source) and the `vite.config.ts` alias (for bundling). The root tsconfig should be:
```json
{
  "files": [],
  "references": [
    { "path": "./tsconfig.app.json" },
    { "path": "./tsconfig.node.json" }
  ]
}
```

### WR-02: `vite.config.ts` proxy does not restrict to `localhost` — any interface binds in `--host` mode

**File:** `frontend/vite.config.ts:15-28`
**Issue:** The proxy target is hardcoded to `http://localhost:5000`. This is correct for normal dev usage. However, if a developer starts Vite with `--host` (to test on mobile/LAN), the Vite server becomes reachable from the network but the proxy still forwards to `localhost:5000` on the host machine. This is not a vulnerability in the proxy config itself, but there is no `server.host` restriction, meaning the setup silently exposes the dev frontend to the LAN when `--host` is used. More importantly, there is currently no `VITE_API_BASE_URL` guard — if the variable is set to a non-empty value in dev (e.g., accidentally copied from a prod `.env`), the React app will bypass the proxy and hit the production backend directly from a developer's machine.

The `frontend/.env.example` correctly leaves `VITE_API_BASE_URL` empty for dev, but the React source files do not yet use this variable at all (Phase 3 concern). Document the intended usage clearly and consider adding a comment in `vite.config.ts` noting the `--host` caveat.

**Fix:** Add a comment, and optionally enforce `server.host: 'localhost'` to prevent accidental LAN exposure:
```ts
server: {
  host: 'localhost', // Remove this if you need --host for device testing
  proxy: { ... }
}
```

### WR-03: `tabs.tsx` has `"use client"` directive — dead/incorrect in a Vite + React SPA

**File:** `frontend/src/components/ui/tabs.tsx:1`
**Issue:** `"use client"` is a Next.js / React Server Components directive. In a plain Vite + React SPA there are no server components; this directive is silently ignored by the bundler but signals to maintainers (and AI code generators) that this file was generated from a Next.js shadcn template rather than the SPA template (`rsc: false` in `components.json`). As Phase 3 adds more shadcn components the same issue may recur. It will not cause a runtime error but it will cause TypeScript linting confusion if a strict `"use client"` checker is ever added.
**Fix:** Remove the `"use client"` line from `frontend/src/components/ui/tabs.tsx`. Audit any future shadcn additions for the same directive.

### WR-04: `backend/requirements.txt` has no version pins — breaks reproducible deploys

**File:** `backend/requirements.txt:1-9`
**Issue:** All nine dependencies are unpinned (e.g., `flask`, `openai`, `faiss-cpu`). When Render installs dependencies it resolves to latest-at-deploy-time. A breaking release of any dependency (the `openai` SDK has had multiple breaking API changes between 0.x, 1.x, and 2.x) will fail the deployment silently or produce a runtime error. The `CLAUDE.md` records exact versions (`openai 2.32.0`, `Flask 3.1.3`, etc.) but those are not reflected in `requirements.txt`.
**Fix:** Pin to the known-good versions documented in `CLAUDE.md`:
```
flask==3.1.3
flask-limiter==4.1.1
requests==2.33.1
openai==2.32.0
python-dotenv==1.2.2
faiss-cpu==1.13.2
pymupdf==1.27.2.2
numpy==2.4.4
gunicorn==25.3.0
```
Also add `resend` (planned for Phase 2 per CLAUDE.md constraints) as an unpinned placeholder so it does not get forgotten.
