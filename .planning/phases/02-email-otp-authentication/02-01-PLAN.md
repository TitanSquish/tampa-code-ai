<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator config → repo | Env var names documented in `.env.example` drive production behavior. Wrong var names or missing vars cause silent insecure defaults (e.g., `SESSION_COOKIE_SECURE=False` in prod if `FLASK_ENV` is unset). |
| PyPI package supply chain | `resend` and `flask-cors` are installed into production runtime. A compromised upstream could exfiltrate `RESEND_API_KEY` or session cookies. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Information Disclosure | `backend/.env.example` committed to git | mitigate | File contains ONLY placeholder values (`re_...`, `change-this-secret`, etc.) — never real secrets. Acceptance criteria explicitly checks RESEND_API_KEY placeholder is `re_...` not a real key. Operators must copy to `backend/.env` (gitignored) and fill real values. |
| T-02-02 | Tampering | PyPI dependency supply chain (`resend`, `flask-cors`) | accept | Following project convention of unpinned deps (see existing `requirements.txt`). Phase 4 deployment may introduce `pip install --require-hashes` but this is out of scope for Phase 2. Risk bounded by Render's managed runtime and the narrow attack surface of two well-known packages (resend is first-party; flask-cors has 20M+ monthly downloads). |
| T-02-03 | Spoofing | `RESEND_FROM_EMAIL` default `onboarding@resend.dev` | mitigate | Default is Resend's sandbox sender which only delivers to the Resend account holder's inbox — this is a FAIL-SAFE default: accidental deployment without a verified domain cannot spam arbitrary recipients. Comment in `.env.example` explicitly calls out the constraint and points to https://resend.com/domains for real deployment. |
| T-02-04 | Elevation of Privilege | Deprecated `APP_LOGIN_PASSWORD` lingering in operator `.env` files | mitigate | `.env.example` is updated to mark the var DEPRECATED and comment it out. Plan 03 removes the consumer (`LOGIN_PASSWORD = os.getenv(...)` line and the `/login` route), so the env var becomes inert. Even if an operator leaves the value in `.env`, no code reads it after Plan 03. |
| T-02-05 | Information Disclosure | `FRONTEND_ORIGIN` leaking in error messages | accept | Value is `http://localhost:5173` in dev; production Render URL is public by nature (Phase 4 deployment concern). Low-sensitivity config. |
</threat_model>
